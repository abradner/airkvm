# Repository Map

> Read this before touching anything boundary-sensitive: auth, tenancy, deletion/visibility,
> serialization, background delivery, routing, any external surface. Update it in the same PR as
> any change that moves an edge here. Never leave it describing a stale security boundary — a
> wrong map is worse than no map, because it is trusted.

## What belongs here — and what doesn't

This is a **boundary map, not a directory tree.** Anything an agent can answer with grep/glob in
seconds — where a symbol is defined, which files match a pattern — does *not* belong here: that
content goes stale fastest and helps least. What belongs is the knowledge that lives *between*
files and can't be reconstructed from any one of them:

- **Surfaces** — every distinct way into the system, each with its auth mechanism.
- **Trust boundaries** — for each edge: who is the caller, how is identity established, and what
  happens if they lie.
- **Cross-cutting flows** — the handful of sequences where one action touches many parts, and
  where a change to one part silently breaks an invariant held elsewhere (the classic: soft-
  deleting a record does nothing to a session that looks it up by ID unless every lookup is
  scoped).
- **Risk register** — numbered, stable IDs for known concentrations of risk, so rules, PRs, and
  code comments can cite them.

Start small and grow by incident: three accurate entries beat thirty aspirational ones. When the
map and the code disagree, the code is the truth and the map is the bug — fix it in the same
change that found the disagreement.

## Surfaces

| Surface | Path / entry point | Auth mechanism | Notes |
|---|---|---|---|
| Console page | `GET /` (HTTPS, port 443) | **None** — transport encrypted, caller unauthenticated | Static page embedded in firmware. Anyone who can route to the dongle gets it. |
| Device settings | `GET /settings`, `POST /settings` (same origin and port as the console) | **None** — see R-010 | The device describes itself (board, features, every runtime setting with its current value and permitted values; `firmware/main/settings_schema.h`) and accepts changes as form-urlencoded, persisting them to NVS (`firmware/main/settings.c`, namespace `airkvm`, one key per setting). Today: the panel theme, panel and LED brightness, the debug row's auto-off (shorten-only), and the USB composition (reboot to apply). Reads are generated JSON with no parser on the device; writes go through the same pure form decoder the setup portal uses (`firmware/main/form.c`), a known value is refused (400) rather than corrected, and commits are rate-limited to one per second so a caller cannot wear the partition out. A stored value this image does not know resolves to the build default and is left in place. Unverified on hardware: the repaint on a theme change (`display_set_theme`) and persistence across a reboot. |
| Input socket | `GET /ws` (WSS upgrade) | **None** — see R-001 | The actual keystroke path. Every input frame here becomes a USB HID report on the target. Also carries the wake request, which is answered here and never becomes a report: on `WAKE` the dongle signals USB remote wakeup to a suspended target and replies with a result frame, one of the protocol's two dongle→console messages, the other being the `STATUS` reply to `STATUS_REQ` (wake unverified on hardware). |
| USB HID device | USB-C port → target machine | **None, by design** | The target cannot authenticate a keyboard. This is inherent to HID, not a gap we can close. |
| USB mass storage | Same port, interface 2 | **None, by design** | A removable-disk LUN (`firmware/main/msc_out.c`), present whenever the stored USB composition includes it (the default; `firmware/main/settings.c`) and then always present so attaching media never re-enumerates. With the disk left out — chosen from the console, applied at the next boot, PID 0x4004 rather than 0x4006 so hosts do not reuse a cached descriptor — there is no LUN, the SD probe and the media socket are not started, and every `msc_out_*` entry point tolerates that (gotcha 16b's rule). Read-only today. Unverified on hardware: whether a BIOS still takes the boot keyboard beside a card reader, and everything about the media path. |
| Media socket | `GET /ws-media` (WSS upgrade, **port 8443**, its own `esp_http_server` instance) | **None** — see R-008 | Attaches a disk image held in the operator's browser (or `firmware/tools/poke.py media`) as the LUN's medium and serves its 16 KB chunks on demand. Closing the socket detaches; a client silent for two request timeouts (8 s) is dropped. Not advertised over mDNS. |
| HTTPS redirect | `GET /*` (plain HTTP, port 80) | **None** — and nothing to authenticate | Answers a bare `http://airkvm.local/` with `302 Found` to the same path on 443, so typing the hostname into a browser reaches the console instead of a refused connection. Anything the validator rejects gets a 400 rather than a guessed `Location`. The server is capped at 2 client sockets with 4-second read/write deadlines so it cannot starve the console's TLS accept out of the shared lwIP pool; `sdkconfig.defaults` carries that arithmetic. Not advertised over mDNS: the `_https` record still points at 443, so service discovery never routes through this. Compiled out entirely on a non-TLS build, where the console itself is on 80. `firmware/main/http80.c` owns port 80 and is also where the log tap's `/log` route is registered, in an order that makes it win over the catch-all. |
| Serial console | UART/USB-JTAG in bootloader mode | Physical access | Flashing and logs. Only present when firmware hasn't claimed USB (AGENTS.md §6.1). |
| Status display + button | On-board panel (SSD1306 72x40 OLED, or ST7789 172x320 LCD) and BOOT button | Physical access | Shows IP, signal (as an RSSI figure and a stepped gauge whose colour tracks the same weak-link threshold the LED uses, `indicator_link_is_weak`), and link state; blanks to an idle animation after 5 minutes with no client input and no local button interaction (the 0.42" dongle has no LED to show it's alive otherwise; the LCD board does, since #40). The button dismisses that animation if it's showing, or toggles a debug view of live input if not — see R-006. |
| WiFi association | Station mode, credentials in NVS | WPA2 (the network's) | The dongle's only network identity is "a device on this LAN". |
| Setup portal | softAP `airkvm-XXXX` (WPA3-SAE only, PMF required, 8-character hex passphrase on the panel), plain HTTP port 80, captive DNS on that link; on the S3 also a USB CDC-NCM network device, 192.168.7.1/24 with its own DHCP server (`firmware/main/usb_net.c`) | **Physical presence** — see R-009 | Only after a 5 s BOOT hold, for 5 minutes, with keyboard, disk and web console all absent (`firmware/main/setup_mode.c`). One page, one POST, writes the STA credentials to the radio's NVS store and restarts. Not a bridge: no forwarding, no route — the USB link's DHCP offer carries no router and no DNS option, so the plugged-in machine gains an address on that link and nothing else, and the captive DNS is bound to the AP address alone. built. Nothing here has run in production. The last column says what backs each row, because it
is not the same thing for all of them.

## Trust boundaries

- **Browser → dongle (`/ws`).** Caller identity is *not established at all*: any host that can
  open a TCP connection to the dongle can send input frames. If the caller "lies" there is
  nothing to lie about — there is no identity to forge. The dongle will happily type for a second
  concurrent client. This is the honest current state, recorded here deliberately (R-001). The
  same caller can wake a suspended target (USB remote wakeup): that is a new *action* on this
  surface, not a new surface, and it is owner-only like every other frame (R-003). The boundary
  does not move — waking a machine you can already type on is what a physical keyboard grants
  too, and the wake button and wake-on-input are the same capability by two routes.
- **Browser → dongle (`/ws-media`).** Same caller identity as `/ws`: none. Any host that can open
  the port can attach a disk image the target will see as a removable disk. That is a real
  widening of R-001 — typing anything was already possible; presenting boot media adds "boot an
  OS of the attacker's choosing" without typing it in — and it is accepted with the same argument:
  plugging the dongle in is the act of trust, unplugging revokes it (R-008). The image is read-only
  by construction, so this edge cannot be used to *exfiltrate* from the target; it can only feed
  it.
- **The plugged-in machine → setup portal, over USB.** On the S3, setup mode enumerates as a
  USB Ethernet adapter on a private link, so the machine the dongle is plugged into can reach
  the same page without joining the AP. That is presence by definition (it is holding the
  dongle), and the link is deliberately a dead end: no default route through it, no resolver
  offered, nothing forwarded (`firmware/main/usb_net.c`). It is the on-ramp a bridge (issue #38) would
  use, and #38 stays parked.
- **Anyone in WiFi range → setup portal.** Reachable only while setup mode is up, which takes a
  hand on the button, and joining needs the passphrase shown on the panel, which takes eyes on
  it. Both are presence. Credentials cross the air under WPA3-SAE keyed by that passphrase (R-009).
- **Dongle → target (USB).** The target trusts the dongle completely and unconditionally: it is
  a keyboard, and now also a disk. No mitigation exists on this edge and none can — a HID device is authorized by
  being plugged in. Everything protecting the target therefore has to live on the *previous*
  edge, which is why R-001 is the top entry.
- **Operator → capture video.** Not a dongle boundary at all: the HDMI capture dongle is a local
  UVC device the *browser* opens via `getUserMedia`. Video never traverses the network and never
  reaches the ESP32. If a future change makes video pass through the dongle, this line is wrong
  and the whole risk profile changes — update it in the same PR.
- **Operator browser → coordinator.** Identity is a password-authenticated session. Tenancy is the
  boundary that matters inside it: an operator of one Account must not learn that another
  Account's records exist, let alone reach them (R-011). Today the coordinator holds operators,
  their sessions and their accounts, so a database breach yields email addresses, password
  hashes, account names, and the addresses and user agents recorded on sessions; a breach of the
  running app also yields `SECRET_KEY_BASE`, which forges any session cookie. The moment devices
  enrol, it becomes every enrolled machine's keyboard, and this line must be rewritten with the
  fleet.md risks.
- **Dongle → internet.** None, and intentionally so. The dongle makes no outbound connections;
  the console loads no remote assets (AGENTS.md §4). Any new outbound call is a boundary change
  requiring an entry here.

## Cross-cutting flows

**Media path**: browser `File.slice()` → `MEDIA_DATA` over `/ws-media` (its own HTTPS instance and
task, so a 16 KB piece never sits in front of a keystroke) → `media_ws.c` decodes and hands the
piece to `block_source_browser.c`'s cache → the `msc_io` worker, blocked in the source's `read`,
copies it out and completes TinyUSB's pending transfer → the target's SCSI stack. Requests flow the
other way from the worker via the media server's work queue. Invariant: **every attach has a
matching detach, or a terminal event that forces one** — `media_ws.c:drop_medium()` is the only
place the medium is dropped, it unbinds the LUN *before* dropping the source so an in-flight
transfer fails on generation, and it is idempotent because socket close and a failed read race for
the same medium. Latency and throughput: unmeasured (principle 6 says so, not "fine").

**Keystroke path** (the one that matters): browser `keydown` → `event.code` → protocol frame over
WebSocket → `firmware/main/protocol.c` decode → intent struct → queue → `firmware/main/hid_state.c` (single owner,
mutates authoritative bitmap) → TinyUSB report → target. The invariant that must survive the whole
traversal: **every key-down has a matching key-up, or a release-all that supersedes it.** Any
stage that can drop a frame (socket close, queue full, task starve) must trigger release-all
rather than let a partial state stand.

**Session lifecycle**: WebSocket open → capture engaged (pointer lock) → frames flow → *any*
terminal event (close, error, page hidden, pointer-lock exit) → release-all. There
is deliberately no "reconnect and resume": resumption would require trusting a state snapshot
across a gap the dongle can't verify, and the failure mode is a stuck key on someone's machine.
Reconnect starts a fresh session with everything released.

**Keepalive**: the console sends a `PING` frame every second, and the device tears the session
down — releasing everything — after 3s without any frame from the owner. A spectator's frames
deliberately do not refresh the deadline; only the owner's.

This **bounds** what was previously an unbounded gap, rather than closing it. A client that
vanishes *without* closing its TCP connection (a suspended laptop, a backgrounded mobile browser)
used to hold state until the socket layer noticed, which could be indefinitely; it is now at most
~3s. The phone console (`soft` mode, `packages/console/app.js`) does not rely on the deadline for the
case it can see coming: going hidden sends release-all itself, and coming back sends one frame
on an open socket (which re-claims the session) or reconnects at once on a closed one. No
boundary moves for the phone: same origin, same two routes, no new asset, no new outbound call. What it does not do is measure client liveness: `esp_http_server` runs a single task for
accepting connections, performing TLS handshakes, serving assets and dispatching WebSocket
frames — serially — so a PING that arrived on time but is queued behind that work is
indistinguishable from silence. A TLS handshake measured ~4.8s on
this hardware at −85 dBm — longer than the deadline — and R-001 means any LAN device can trigger
one unauthenticated. **So an operator holding a chord can lose it because someone reloaded the
console.** That trade is deliberate (principle 4 prefers a spurious release to a held key), and
the real fix — detecting a vanished peer where head-of-line blocking cannot reach it — is issue
#6, not done.

**Boot/provisioning**: stored credentials (NVS — written by setup mode, or by a previous boot's Kconfig values; Kconfig itself only on a fresh flash) → WiFi station init → mDNS advertise (`airkvm.local`, or
`airkvm-lcd.local` on the second board — each dongle needs its own name and its own certificate,
since the name is what the certificate is issued for) →
HTTPS server up → USB HID → address shown on the OLED and logged to serial. WiFi's *synchronous*
init runs before USB HID, and that order is load-bearing: the S3's RF PHY and USB PHY share the
BBPLL, and TinyUSB claiming it first leaves WiFi unable to associate at all (AGENTS.md §9, entry
10). HID still does not wait on the *network* — `net_start()` returns as soon as association is
started, and HID starts even if that init fails: a dongle with no WiFi is still a keyboard that
can be driven once the network returns, and must never block enumeration on an association that
may never happen.

## Risk register

| ID | Risk | Where it lives | Mitigation / status |
|---|---|---|---|
| R-001 | Unauthenticated LAN input: anyone routable to the dongle can type on the target | `/ws` handler | **Accepted, documented, unmitigated.** The security model is physical: plugging it in is deliberate, unplugging revokes completely. Do not deploy on untrusted networks. A shared-secret/PIN gate is the obvious first mitigation if this ever runs somewhere less trusted — not built. |
| R-002 | Stuck keys on the target after a network or firmware fault | `firmware/main/hid_state.c`, `firmware/main/session.c` | Single-owner HID state + release-all on every terminal event (AGENTS.md §4, §2 principle 4). Session ownership is its own state machine, so every terminal event funnels through one release path, and a silent client is torn down on a 3s deadline rather than held indefinitely. The state machine is host-tested; the release path itself is unverified on hardware. |
| R-003 | Two concurrent console clients interleaving input into one HID state | `/ws` handler | **Partially mitigated.** One controlling session is tracked (`s_active_fd`); a second client's frames are accepted at the HTTP layer and then ignored (`firmware/main/net.c`), so streams never interleave. Not built: telling that second client it is a spectator, and explicit takeover. |
| R-004 | WiFi credentials stored in plaintext NVS; physical recovery of the dongle exposes them | NVS partition (esp_wifi's own store, written by `esp_wifi_set_config` from Kconfig on first boot and by setup mode thereafter) | Accepted for now — a lost dongle is already a lost keyboard-on-the-LAN. Flash encryption is the real answer if this ever leaves a home network. |
| R-005 | Firmware claims about hardware behavior that has never run on hardware | Everywhere | Marked in-place as unverified (AGENTS.md §4, last rule). Clears when a board arrives and the phase-1 enumeration test passes. |
| R-008 | Unauthenticated LAN media: anyone routable to the dongle can present a disk image to the target, including boot media | `/ws-media` handler (`firmware/main/media_ws.c`), `firmware/main/block_source_browser.c` | **Accepted, documented, unmitigated — the same posture as R-001, and the same mitigation: physical presence.** Bounded in three ways by construction: the medium is read-only (the LUN refuses WRITE with DATA PROTECT; a source's read/write is never invoked for it), one client can connect at a time (the storage twin of R-003, enforced at the socket), and every terminal event — DETACH, socket close, WiFi loss — drops it totally, so a transfer in flight against a vanished image fails with NOT READY rather than delivering stale bytes. On the LCD147 board the medium can also be a **microSD card** (`firmware/main/msc_src_sd.c`, `CONFIG_AIRKVM_MSC_SD`): an inserted card is input the firmware did not author, accepted with the same argument (inserting it is a deliberate physical act). It is read-only, so the target cannot leave data on the card through the dongle; a card still leaves carrying whatever it arrived with, which is the physical-presence boundary again. The write mode (#34's neighbour) lets the target write to it and must say so here when it lands. Card and browser image are exclusive: the first to arrive holds the LUN. A shared-secret gate, if ever built for R-001, must cover this socket too. |
| R-009 | Setup portal: anyone within WiFi range who can read the panel can re-point the dongle at a network of their choosing | `firmware/main/setup_mode.c` | **Accepted, by the physical-presence argument, and bounded:** the mode exists only after a deliberate 5 s hold, for 5 minutes, with the 8-character hex passphrase on the panel (reading the panel *is* presence); HID, storage and the console are absent while it runs, so the target cannot be typed at or fed media during the window; the captive DNS is bound to the AP address alone. The USB network link (S3 only, `firmware/main/usb_net.c`) widens nothing: it is reachable only from the machine physically holding the dongle, and it carries no route, no DNS and no forwarding, so it cannot be used to reach the AP side or anything beyond the setup page. Unverified on hardware: that the host's route table and resolver are in fact untouched is the acceptance test, not the descriptor. The AP is WPA3-SAE **only** (not WPA2/WPA3 mixed, which would offer a downgrade): SAE is a PAKE, so a handshake captured from the air cannot be attacked offline, and the 32-bit passphrase only has to beat online guessing at the AP's own association rate. An earlier version of this entry accepted an 8-digit key under WPA2 as crackable in minutes from a captured handshake; that weakness is removed rather than slowed (decision 2026-09-07). The cost, accepted with it: clients older than iOS 13 / Android 10 cannot join the setup AP. Unverified on hardware: that the AP actually comes up in WPA3-only mode with PMF required and that a current phone joins it. **The panel's brightness is now a setting** (R-010) and this argument is why it has a floor (`SETTINGS_SCREEN_MIN`, refused below it on the wire and defaulted from flash) and why `ui.c` forces full brightness for as long as setup mode runs, whatever is stored — a caller who could blank the panel could blank the proof of presence. |
| R-007 | Keystrokes cross the network in plaintext | `/ws` | **Mitigated, and verified on hardware 2026-09-05** — a full TLS 1.2 handshake (ECDHE-RSA-AES256-GCM-SHA384), the console served over HTTPS, and keystrokes delivered over WSS and confirmed arriving as real HID. Until that date this was mitigated only in intent: the handshake crashed the firmware (issue #24, AGENTS.md §9 entry 13), so the console was unreachable rather than insecure. The console is served over HTTPS/WSS with a certificate issued by an operator-run CA (`firmware/tools/make_certs.sh`); the console is not served over plain HTTP at all, and TLS failing to start is fatal rather than falling back — a silent downgrade would leave keystrokes readable while everything still appeared to work. **Port 80 is now open on a TLS build and serves a 302 to 443** (`firmware/main/http80.c`) — plus `/log` on a diagnostic build, which is R-006's problem and was already on that port. It carries no console, no assets and no socket, so there is no content to read off it and no downgrade path — a client that follows it ends up on TLS, and one that does not gets a link and no data. The redirect is deliberately 302 and not 301, and not HSTS: both of those outlive the firmware that sent them, and this project supports building with `AIRKVM_TLS=n`, where a cached permanent upgrade would break a working plain-HTTP console in a way only clearing browser state fixes. Note this encrypts the transport only: R-001 is untouched, because anyone who trusts the CA and can reach the device can still connect and type. |
| R-006 | The status display can show what is being typed — passwords included — to anyone who can see the device | `firmware/main/ui.c`, `firmware/main/status.c` | **Gated on physical presence, and now time-limited.** Debug rows are off at boot, toggled only by the on-board button, and there is deliberately no network path to enable them. The button does double duty (also dismissing the idle screensaver), so what a press does depends on whether the screensaver is showing at the moment of that press — latched at press time specifically so a client HID event landing mid-press can't retarget an already-committed press onto the other action. While off, keystroke text is not merely hidden but never stored (`status_note_event` discards it), and toggling off wipes the buffer — so a future logging change cannot leak a value that was captured "just in case". **The residual risk grew when the LCD board landed:** the mitigation's argument is that anyone who can press the button could already unplug the device, which silently assumed the row is only legible from arm's reach. On the 0.42" OLED a 3x5 glyph is 0.39 x 0.65 mm and readable at perhaps 30 cm — inside reach of the button, so the two facts held together. On the 1.47" LCD the *smallest renderable* glyph is 0.82 x 1.64 mm, 2.5x the linear size, because that panel's pixels are smaller but the minimum legible glyph is bigger. No font size on it reproduces the OLED's exposure, so someone at 2-3 m who cannot reach the button can read the row. Mitigations: the debug row is rendered at the smallest cell the panel has and never enlarged (a security parameter, not a layout one — see the comment in `ui.c`), it is drawn in the same quiet ink as the rest of the panel, never in the accent colour, and explicitly in `DISPLAY_HUE_NEUTRAL` now that sections carry hues — so no future reordering of `draw()` can hand the keystroke row a colour that draws the eye to it, and debug mode now turns itself off after a timeout that is **at most** `STATUS_DEBUG_TIMEOUT_MS` (5 min) — settable shorter from the console (R-010) and never longer: `status_debug_timeout_clamp` in `status.h` is the enforcement, applied by the value's one owner, and the settings schema refusing a larger number on the wire is politeness that could be deleted without making a longer window possible. **The residual risk grew again when the panel became themeable** (`firmware/main/theme.h`): the row is drawn in the SECONDARY ink role, whose contrast against the background went from 2.9:1 to 7.9:1 in the default theme, so it is now materially easier to read across a room than it was. That is not a regression to fix — raising SECONDARY contrast is the entire point of the change, and every other row on the panel benefits identically — but it is a real widening and it is recorded rather than absorbed. The alternatives were both worse: a fifth ink role for "legible but not from over there" needs a third 1bpp plane (7KB of heap this board has already spent), and choosing a low-contrast colour for this row alone is security by squinting. If the row's legibility ever becomes the binding concern, the answer is not rendering it at all, not dimming it. The timeout lives in `status.c` next to `status_toggle_debug()` and is **not** gated on the board: enforcement exists once, so the shipping OLED dongle gets it too. Physical presence is a fact about the moment of the press, not the following hour. |
| R-010 | LAN-writable device configuration: anyone routable to the dongle can change what it is set to | `/settings` (`firmware/main/net.c`, `firmware/main/settings.c`) | **Accepted, by the physical-presence argument, and bounded by what the surface can reach.** It reaches cosmetics — the panel theme, panel and LED brightness — the debug row's auto-off timeout (shorten-only), and which USB interfaces the dongle presents — stored now, applied at the next boot, with a restart the caller can request **only while such a change is pending**: a bare restart is refused, so the surface is not a button for knocking the keyboard off the target, though a caller can of course change the composition and then restart, which R-001 already permits by other means. It does **not** reach WiFi credentials (those are written only by the setup portal, which needs a 5 s BOOT hold), the debug row's *enable* (button only, R-006), or the LED's meaning (`firmware/main/palette.h` keeps `SOL_LED_*` outside the theme: a theme changes what the panel looks like, never what the light means). Two things the surface must never be allowed to do, stated here so a later setting is measured against them: **blank the panel** — R-009 depends on the setup passphrase being readable off it, so any brightness setting clamps to a visible floor and setup mode forces full brightness; and **lengthen R-006's debug timeout** — a network-set timeout may only shorten the compile-time default, or a caller could pre-set the maximum and wait for a press. Flash wear is bounded by write-on-change plus a one-per-second commit limit; the write runs on the single HTTP task, so a burst of changes delays keystroke dispatch by one NVS commit at most. Same mitigation as R-001 for everything else: plugging it in is the act of trust. |
| R-011 | Cross-tenant access in the coordinator: one Account's operator reaching, or learning of, another Account's records | `coordinator/app/controllers/` — every lookup | **Mitigated by convention plus a spec per resource, not mechanically.** Every tenant-scoped read goes through `current_account.<association>`, never the bare class — the only global lookups are the two that happen before a tenant is known (the session cookie's row, and the email address at sign-in, which is unique service-wide for exactly that reason) — and another Account's id is a 404 byte-identical to an id that never existed (`spec/requests/operators_spec.rb`, seen to fail with `User.find` planted). Nothing stops a new controller using the bare class; the rule is in `coordinator/AGENTS.md` §4 and each new resource brings its own cross-account spec. When devices arrive this stops being about email addresses and becomes about who can type on whose machines. |
| R-012 | First-boot takeover: on a fresh self-hosted install, whoever reaches `/setup` first creates the Account and becomes its first operator | `coordinator/app/controllers/setups_controller.rb`, `coordinator/app/models/first_boot.rb` | **Accepted for the self-hosted edition, bounded, and unreachable in the cloud edition.** The window runs from first boot until setup completes, and the install is on the operator's own infrastructure — the same "the deliberate act is yours" argument as R-001, with the same caveat about untrusted networks; the README says to complete setup before exposing the service. Completion is serialised by a Postgres advisory lock and re-checked under it, so two simultaneous requests cannot both succeed (`spec/models/first_boot_race_spec.rb`, seen to fail with the lock removed). **The window is derived, not stored: it is open whenever no Account exists**, so emptying the accounts table (a console, or a future account-deletion feature) reopens it to anyone who can reach the page — pinned by `spec/requests/setup_spec.rb`. Nothing in the app deletes an Account today. In the cloud edition the page is always 404, and `AIRKVM_EDITION` has no production default, so a cloud deploy cannot fall back into the self-hosted policy. A setup token printed to the server log would close the window; not built. **Host header:** production refuses to boot without `COORDINATOR_HOSTS` and answers no other `Host` (`config/initializers/require_hosts.rb`, `spec/smoke/boot_spec.rb`; #88, decided 2026-11-09), so a DNS-rebinding page in an operator's browser cannot reach `/setup` during the window — previously only the TLS certificate and the `Secure` cookie stood in the way, neither designed as protection. **Accepted 2026-11-09 with a standing constraint:** any future account-deletion feature must refuse to delete the last Account, or must re-gate `/setup` (a stored completion marker), in the same change. A refused `Host` is logged by Rails as one error line per request, quoting the attacker-chosen name. |
